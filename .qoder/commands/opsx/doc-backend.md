基于已完成的 OpenSpec 计划产物，生成一份面向研发评审的「开发设计文档」。

**定位**：这是把 OpenSpec 的「计划产物」（proposal 讲 why/what、specs 讲行为契约、design 讲技术方案）翻译成一份团队评审用的「开发设计文档」。它面向人（研发、产品、测试、评审会），强调每个需求的改造细节、接口、数据、流程，而不是 OpenSpec 内部的文件结构。

**前置条件**：变更必须先完成 `/opsx:propose`，即变更目录下已存在 proposal.md、specs/、design.md（design 可缺省）。若这些产物不存在，提示用户先执行 `/opsx:propose`，不要凭空捏造内容。

**输入**：可选指定变更名（如 `/opsx:doc-backend add-user-login`）。若省略，从上下文推断；若有多个变更或模糊，用 `openspec list` 让用户选一个。

**输出位置**：写入变更目录下 `openspec/changes/<变更名>/doc-backend.html`（HTML 格式）。

**步骤**

1. **确定变更名**，并定位变更目录 `openspec/changes/<变更名>/`。

2. **读取计划产物**（务必从磁盘重新读取，不要只凭记忆）：
   - `proposal.md`：为什么做、改什么、涉及哪些能力（Capabilities）
   - `specs/` 下的所有 `spec.md`：需求与验收场景（行为契约）
   - `design.md`（若存在）：技术方案、决策、风险
   - `tasks.md`（若存在）：实现步骤，可辅助拆分需求

3. **按下方模板结构生成文档**。核心原则：
   - 把 proposal 里的「What Changes / Capabilities」拆成一个一个独立「需求」，每个需求一节
   - 每个需求都要落到「接口、数据存储、流程」这些可评审的工程细节上；proposal/specs 里没有的信息，要基于 design 和代码推断，**推断的、待定的、拿不准的，一律放进「待确认事项」**，不要编造确定结论
   - 接口设计要给出字段表（字段/类型/必填/说明）
   - 数据存储要说明新增哪些表、哪些字段、是否复用
   - 流程用 PlantUML 时序图表达（钉钉文档可渲染 plantuml 代码块）

4. **写完后自检**：每个需求是否覆盖了「需求回顾 / 方案说明 / 流程 / 接口 / 数据 / 待确认」，是否有编造的外部接口或表结构。

**文档模板**（严格按此结构）：

```markdown
# <项目/变更> 开发设计文档

> 需求来源：`openspec/changes/<变更名>/`（proposal.md / specs / design.md）

## 一、改造总览

| # | 需求 | 核心改造 | 前端接口 | 新增表/字段 | 外部依赖 |
|---|------|----------|----------|-------------|----------|
| 1 | <需求名> | <一句话核心改造> | <新增/复用的接口> | <新增表或字段，无则「无」> | <外部系统，无则「无」> |

## 二、需求一：<需求名>

### 2.1 需求回顾
<!-- 从 proposal/specs 提炼：入口、触发条件、期望行为，用要点列 -->

### 2.2 方案说明
<!-- 逐条说明技术方案：怎么做、为什么这么做、是否可配置、是否复用现有能力 -->

### 2.3 整体流程
<!-- 用 PlantUML 时序图表达核心交互；多流程可分多个图 -->

### 2.4 接口设计
<!-- 每个接口给出：方向（出参/入参）、字段表（字段/类型/必填/说明）、交互规则/异常 -->

### 2.5 数据存储
<!-- 新增表结构、新增字段、缓存、复用情况，用表格 -->

### 2.6 待确认事项
<!-- 表格：事项 / 责任方 / 状态（待确认） -->

## 三、需求二：<需求名>
<!-- 同上，节号递增 -->

## 五、整体节奏建议
<!-- 哪些需求可先行开发、哪些有外部依赖阻塞、建议的评审认领 -->
```

**输出格式**：生成带内嵌 CSS 样式的 HTML 文档（`doc-backend.html`），要求：
   - 包含完整的 HTML 结构和内嵌 CSS 样式（专业、可打印）
   - 表格使用彩色标签标注变更类型（删除=红、新增=绿、修改=蓝、待确认=黄、不变=灰）
   - PlantUML 时序图必须可渲染：使用 `<div class="plantuml-rendered">` + `<pre class="plantuml-src">` 结构，页面底部内嵌 pako CDN + PlantUML server 编码 JS，实现浏览器端自动将 PlantUML 渲染为 SVG 图片；**注意 pako.deflateRaw() 必须接收 `Uint8Array` 而非普通 JS 数组**；源码默认隐藏，提供“查看源码”切换按钮
   - 非 PlantUML 的代码片段用 `<pre><code>` 包裹，深色背景
   - 文档模板结构（章节、表格、字段）与上方 markdown 模板一致，只是输出格式为 HTML

**Guardrails**
- 本命令只产出 `doc-backend.html`，不修改 proposal/specs/design/tasks，不改任何业务代码
- 只做「计划产物 → 开发设计文档」的翻译与补全，不重新规划需求范围
- 所有不确定项（外部接口报文、表名/字段终值、鉴权方式等）显式标注「待确认」，绝不编造
- 生成后简要说明文档位置与各需求小节，提示用户评审
